## 1. Scope

**In scope**

- Customer accounts in SGD, USD, EUR and JPY.
- Deposits from outside the ledger.
- Transfers between customer accounts, in the same currency or across currencies.
- Reversals.
- Idempotent money-moving requests.
- Concurrency-safe balance updates.
- An on-demand integrity check.
- Month-end reconciliation, run manually or on a schedule.

**Out of scope:** authentication and authorization, withdrawals, closing accounts, partial reversals, FX revaluation and P&L, running several instances, any UI.

### 2.1 Why plain JDBC instead of JPA **[added]**

The write path depends on things that JPA hides:

- the exact SQL used for locking (`ORDER BY id FOR NO KEY UPDATE` in a single statement, §6.2);
- the exact moment the unique-constraint violation is raised (on the `INSERT`, not at some later flush or commit, §7.4);
- reading the violated constraint's name.

The tables are append-only, so JPA's dirty checking adds nothing. `JdbcClient` keeps the SQL visible and testable. If JPA is preferred anyway, use `saveAndFlush` for the transaction row and native queries for locking.

## 3. Domain model

### 3.1 Double-entry

- Every movement of money is a **transaction** made up of two or more **entries**.
- An entry is a signed amount posted to one account:
  - **positive** means money into the account (credit, from the account's point of view);
  - **negative** means money out of the account (debit).
- The entries of a transaction **sum to zero per currency**.
- Entries and transactions are **append-only**. Nothing is ever updated or deleted. Mistakes are corrected by posting a reversal.
- `accounts.balance` is a **cached** value of `SUM(entries.amount)` for that account. It is updated in the same database transaction that inserts the entries, and the integrity check verifies it.

### 3.2 Accounts

| Field | Notes |
|---|---|
| `id` | UUID. Generated by the application with `UUID.randomUUID()` for customer accounts; fixed values for system accounts. |
| `name` | 1–200 characters. Not unique for customers. Unique among system accounts. |
| `currency` | One of `SGD`, `USD`, `EUR`, `JPY`. Cannot be changed. |
| `type` | `CUSTOMER` or `SYSTEM`. The API can only create `CUSTOMER` accounts. |
| `balance` | Cached sum of the account's entries. May be negative **only** for `SYSTEM` accounts. |
| `created_at` | UTC, taken from the `Clock`. |

### 3.3 System accounts

Seeded by migration with fixed UUIDs, so tests and documentation can refer to them:

| Name | ID | Purpose |
|---|---|---|
| `EXTERNAL_SGD` | `00000000-0000-0000-0000-000000000101` | Source of SGD deposits |
| `EXTERNAL_USD` | `00000000-0000-0000-0000-000000000102` | Source of USD deposits |
| `EXTERNAL_EUR` | `00000000-0000-0000-0000-000000000103` | Source of EUR deposits |
| `EXTERNAL_JPY` | `00000000-0000-0000-0000-000000000104` | Source of JPY deposits |
| `FX_POOL_SGD` | `00000000-0000-0000-0000-000000000201` | SGD side of FX conversions |
| `FX_POOL_USD` | `00000000-0000-0000-0000-000000000202` | USD side of FX conversions |
| `FX_POOL_EUR` | `00000000-0000-0000-0000-000000000203` | EUR side of FX conversions |
| `FX_POOL_JPY` | `00000000-0000-0000-0000-000000000204` | JPY side of FX conversions |

How to read the system balances:

- `EXTERNAL_<CCY>` is always ≤ 0. Its absolute value is the net money deposited into the ledger in that currency.
- An `FX_POOL_<CCY>` balance is the house's net FX position in that currency. Rounding differences from conversions stay in these pools.

**System accounts cannot be used as the source or destination of `POST /transactions`, and cannot receive deposits [added].** Otherwise a client could transfer out of `EXTERNAL_<CCY>`, which is allowed to go negative, and create money from nothing. System accounts are touched only by the posting rules in §5.

### 3.4 Money

- Amounts are `BigDecimal` in Java and `NUMERIC(38,4)` in the database.
- The number of decimal places allowed per currency comes from `java.util.Currency.getDefaultFractionDigits()`: SGD/USD/EUR = 2, JPY = 0.
- The only rounding happens in FX conversion, using `RoundingMode.HALF_EVEN`, to the destination currency's decimal places.
- **Input amounts**:
  - Accepted as a JSON string (`"100.05"`, preferred) or a JSON number. Numbers are parsed straight to `BigDecimal` (`USE_BIG_DECIMAL_FOR_FLOATS`), never through `double`.
  - Must be > 0 (otherwise 400).
  - After `stripTrailingZeros()`, the scale must be ≤ the currency's decimal places (otherwise 400). So `"100.10"` is valid for USD, and `"100.0"` is valid for JPY.
  - Must be ≤ `1000000000000` (10¹²) **[added]**, which keeps sums far inside the column precision.
- **Output amounts** are JSON strings formatted to the currency's scale (`"74.16"`, `"15000"`).

### 3.5 Time

- All timestamps come from the injected `Clock` and are stored as `TIMESTAMPTZ` in UTC.
- Values are truncated to microseconds (`Instant.now(clock).truncatedTo(ChronoUnit.MICROS)`) **[added]**. PostgreSQL stores microseconds, so a value with nanoseconds would not compare equal after a round trip.
- All entries of a transaction share the transaction's `created_at`.
- The API uses ISO-8601 UTC timestamps, for example `2026-10-14T06:31:00Z`.

```sql
    id          UUID          PRIMARY KEY,
    name        VARCHAR(200)  NOT NULL,
    currency    CHAR(3)       NOT NULL CHECK (currency IN ('SGD','USD','EUR','JPY')),
    type        VARCHAR(16)   NOT NULL CHECK (type IN ('CUSTOMER','SYSTEM')),

CREATE UNIQUE INDEX accounts_system_name_uq ON accounts (name) WHERE type = 'SYSTEM';

CREATE TABLE transactions (

    type                     VARCHAR(16)   NOT NULL CHECK (type IN ('DEPOSIT','TRANSFER','REVERSAL')),
    idempotency_key          VARCHAR(255)  NOT NULL,
    request_hash             CHAR(64)      NOT NULL,            -- hex SHA-256, see §7.3
    reverses_transaction_id  UUID          NULL REFERENCES transactions (id),
    fx_rate                  NUMERIC(20,10) NULL CHECK (fx_rate > 0),

    CONSTRAINT transactions_reverses_uq        UNIQUE (reverses_transaction_id),

    CONSTRAINT transactions_fx_rate_type  CHECK (fx_rate IS NULL OR type IN ('TRANSFER','REVERSAL'))
);
CREATE INDEX transactions_created_at_idx ON transactions (created_at, id);

CREATE TABLE entries (
    id              BIGSERIAL     PRIMARY KEY,
    transaction_id  UUID          NOT NULL REFERENCES transactions (id),
    account_id      UUID          NOT NULL,

    currency        CHAR(3)       NOT NULL,
    created_at      TIMESTAMPTZ   NOT NULL,

);
CREATE INDEX entries_account_history_idx ON entries (account_id, created_at, id);
CREATE INDEX entries_transaction_idx     ON entries (transaction_id);
```

```sql
-- V5__append_only_truncate_and_reports.sql  [added]
-- Row triggers don't fire on TRUNCATE, so each append-only table also gets a statement trigger.
-- The reconciliation report tables become append-only too, so GET /reconciliations/{id} returns a run
-- exactly as it was produced (§8.13).

CREATE TRIGGER entries_no_truncate           BEFORE TRUNCATE ON entries           FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();
CREATE TRIGGER transactions_no_truncate      BEFORE TRUNCATE ON transactions      FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();
CREATE TRIGGER balance_snapshots_no_truncate BEFORE TRUNCATE ON balance_snapshots FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();
CREATE TRIGGER exchange_rates_no_truncate    BEFORE TRUNCATE ON exchange_rates    FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();

-- reconciliations, reconciliation_accounts, reconciliation_discrepancies: each gets
--   <table>_append_only  BEFORE UPDATE OR DELETE  FOR EACH ROW
--   <table>_no_truncate  BEFORE TRUNCATE          FOR EACH STATEMENT
-- both executing forbid_mutation().
```

Notes:

- **Source and destination** are not stored on `transactions`. They are derived from the entries (§5.5), so they cannot disagree with them.
- **`accounts.balance`** is the only mutable money column. The `accounts_customer_non_negative` CHECK is a database-level backstop for the application's funds check.
- **Append-only tables**: `entries`, `transactions`, `balance_snapshots`, `exchange_rates`, `reconciliations`, `reconciliation_accounts` and `reconciliation_discrepancies`. Triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on each. They protect against mistakes, not against the table owner, who can drop them (§16.3).
- **Testing tampering.** The integrity and reconciliation tests need to tamper with data. Test-only SQL (run with `JdbcTemplate`) may only do two things:
  - `INSERT` into the append-only tables;
  - `UPDATE accounts.balance`.

  It never updates or deletes entries, transactions, snapshots or rates, and never turns the triggers off. Tests therefore exercise the triggers as they run in production. Production code never does any of this. See §14.2 for the scenarios.

## 5. Posting rules

Notation: `A`/`B` are customer accounts. `amt` is the request amount, in the source currency.

### 5.1 Deposit: `POST /accounts/{A}/deposits`

| Account | Amount | Currency |
|---|---|---|
| `EXTERNAL_<ccy(A)>` | −amt | ccy(A) |
| `A` | +amt | ccy(A) |

`fx_rate = NULL`. Accounts locked: `{A, EXTERNAL_<ccy(A)>}`.

### 5.2 Same-currency transfer: `POST /transactions`, where ccy(A) = ccy(B)

| Account | Amount | Currency |
|---|---|---|
| `A` | −amt | ccy |
| `B` | +amt | ccy |

`fx_rate = NULL`. Accounts locked: `{A, B}`.

### 5.3 Cross-currency transfer: `POST /transactions`, where ccy(A) = S ≠ ccy(B) = D

`rate` is the rate for the pair (S → D) that the transfer reads inside its transaction, after taking its locks: the latest committed rate with `effective_from` ≤ the transaction's `created_at` (§10.1). It is stored on the transaction as `fx_rate`, which is the record of truth for the conversion (§10.2). The destination amount is `dAmt = (amt × rate).setScale(digits(D), HALF_EVEN)`.

| Account | Amount | Currency |
|---|---|---|
| `A` | −amt | S |
| `FX_POOL_S` | +amt | S |
| `FX_POOL_D` | −dAmt | D |
| `B` | +dAmt | D |

- `fx_rate = rate`.
- Accounts locked: `{A, B, FX_POOL_S, FX_POOL_D}`.
- No rate for the pair → **422**.
- `dAmt` rounds to zero (for example 1 JPY → EUR at a rate below 0.005) → **422** `amount-too-small` **[added]**.

Example: Alice (SGD) sends `100.05` SGD to Bob (USD) at SGD→USD `0.7412`. Then 100.05 × 0.7412 = 74.157060, which rounds to **74.16 USD**.

| Account | Amount |
|---|---|
| Alice | −100.05 SGD |
| FX_POOL_SGD | +100.05 SGD |
| FX_POOL_USD | −74.16 USD |
| Bob | +74.16 USD |

### 5.4 Reversal: `POST /transactions/{T}/reversals`

A new `REVERSAL` transaction:

- `reverses_transaction_id = T`.
- One entry for each entry of T: same account, same currency, **negated amount**. FX legs are negated at the **original** amounts. The current rate is never used.
- `fx_rate` is copied from T, for information only.
- Accounts locked: every account that appears in T's entries, system accounts included.
- `created_at` is *now*. A reversal is posted in the current period and never backdated, so periods that are already closed stay unchanged.

Rules:

| Condition | Result |
|---|---|
| T does not exist | 404 |
| T is itself a `REVERSAL` | 422 `reversal-not-allowed` |
| T has already been reversed | 409 `transaction-already-reversed` **[added: status code]** |
| Any customer account would end up negative (for example, Bob has already spent the 74.16 USD) | 422 `insufficient-funds` |

The "already reversed" check runs **after** the account locks are taken. The `transactions_reverses_uq` constraint backs it up (§7.5).

### 5.5 Source and destination, derived from entries

Leave out entries on `FX_POOL_*` accounts. Exactly one entry remains with a negative amount (the **source**) and one with a positive amount (the **destination**). This holds for all three types:

- a deposit's source is `EXTERNAL_<CCY>`;
- a reversal's source is the original transaction's destination.

### 5.6 Assertion before commit

Before the posting method returns, it asserts two things. If either fails, it throws `LedgerInvariantViolation`: the transaction rolls back and the client gets 500 `ledger-invariant-violation`, logged at ERROR.

1. For each currency, `Σ entry.amount = 0`.
2. Every customer account touched has a resulting balance ≥ 0.

## 6. Write path: atomicity and concurrency

### 6.1 One method per write

Each money-moving operation is exactly one `@Transactional` method on `PostingService`:

- `deposit(...)`
- `transfer(...)`
- `reverse(...)`

They use the PostgreSQL default isolation, **READ COMMITTED**. The steps below depend on each statement seeing a fresh snapshot after a lock wait, so these methods must not be switched to REPEATABLE READ.

Steps inside the method:

1. **Resolve the accounts.**
   - Read the accounts named in the request, without locks. Unknown → 404.
   - Validate the amount's decimal places against the source currency → 400.
   - Reject `SYSTEM` accounts → 422. This comes after the 400 check, following the order in §9: request validation before business rules.
   - Work out the full set of account IDs to lock, from §5. `currency` and `type` never change, so it is safe to read them before locking.
2. **Lock** all of those IDs in one statement (§6.2).
3. **Re-check idempotency** (§7.4, step 5).
4. **Check business rules**: rate lookup, funds, reversal state → 422 / 409.
5. **Insert** the `transactions` row. A unique violation is raised here.
6. **Insert** the entries.
7. **Update balances** with `UPDATE accounts SET balance = balance + :delta WHERE id = :id`, once per account.
8. **Assert** the invariants (§5.6).
9. Commit.

Any exception rolls back the whole transaction. For an insufficient-funds 422, nothing is written: no transaction row, no entries, no balance change, and no stored idempotency key.

### 6.2 Lock ordering

```sql
SELECT id, currency, type, balance
FROM accounts
WHERE id IN (:ids)
ORDER BY id
FOR NO KEY UPDATE;
```

`IN (:ids)` is `JdbcClient` expanding the ID collection into one placeholder per ID. It is equivalent to `id = ANY(:ids)` and avoids binding a `uuid[]`. What matters is that this is one statement with `ORDER BY id`.

- **The ordering is done in SQL, in one statement.** PostgreSQL's locking step runs above the sort, so rows are locked in ascending `uuid` order.
- **Do not sort the IDs in Java and lock them one by one.** `java.util.UUID.compareTo` compares signed 64-bit halves. PostgreSQL compares `uuid` as unsigned bytes. The two orders differ, and mixing them can deadlock.
- Every write path locks only through this query, so all transactions take locks in the same global order. Wait cycles can't form, and there are no deadlocks.
- Balances are read *after* the lock is taken, so the funds check sees the latest committed balance. Concurrent transfers out of the same account are serialized, and none of their updates is lost.
- **`FOR NO KEY UPDATE`, not `FOR UPDATE`.** `FOR NO KEY UPDATE` conflicts with itself, so postings still wait for each other exactly as before. It doesn't conflict with `FOR KEY SHARE`, the lock a foreign-key check takes on the referenced account when a row pointing at it is inserted. A posting only changes `balance`, which is in no key, so `FOR NO KEY UPDATE` is also the lock its own `UPDATE` takes. With `FOR UPDATE`, PostgreSQL treats the later balance update as one that may have changed the key. Then:
  - an insert referencing a locked account (a reconciliation's report lines and snapshots) waits for the posting to commit;
  - under REPEATABLE READ it then fails with `40001 could not serialize access due to concurrent update`, because the account row changed after the run's snapshot.
  
  `ReconciliationUnderLoadIT` reproduces that interleaving.

### 6.3 Hot spots (accepted)

System accounts are locked too, so the following are serialized:

- all deposits in one currency (they all lock `EXTERNAL_<CCY>`);
- all FX transfers that touch a given currency (they lock `FX_POOL_<CCY>`).

That is fine at this project's scale. The usual fix, if it ever matters, is to shard the system accounts (for example `EXTERNAL_SGD_0..n`) or to keep system balances out of the hot path. This is noted, not implemented.

## 7. Idempotency

### 7.1 Which requests need a key

`Idempotency-Key` is **required** on:

- `POST /accounts/{id}/deposits`
- `POST /transactions`
- `POST /transactions/{id}/reversals`

| Header state | Result |
|---|---|
| Missing or blank | 400 `missing-idempotency-key` |
| Longer than 255 characters, or not printable ASCII | 400 `invalid-idempotency-key` |
| Present on any other endpoint | Ignored |

The header is required, not optional. Without it the service can't tell a retry from a new request, so it couldn't keep the assignment's promise that repeating a request doesn't cause an extra transfer.

The 400 response names the header and explains why it is needed:

```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "type": "/problems/missing-idempotency-key",
  "title": "Idempotency-Key header required",
  "status": 400,
  "detail": "POST /transactions moves money, so it requires an Idempotency-Key header. Send a unique value (a UUID is fine) for each new request, and send the same value again when you retry it. The ledger uses the key to make sure a request is never applied twice.",
  "instance": "/transactions",
  "header": "Idempotency-Key"
}
```

`invalid-idempotency-key` has the same shape. Its `detail` gives the rule that was broken: 1–255 printable ASCII characters.

### 7.2 Scope and retention **[added]**

- Keys are **global**. They are not scoped per endpoint or per client, because there is no client identity.
- Keys are kept **forever**, because they live on the immutable transaction row.
- The operation type is part of the request hash. So reusing a deposit's key for a transfer is "same key, different body" → 409.

### 7.3 Request hash **[added]**

The hash is the hex SHA-256 of a canonical string that includes the operation and its path parameters:

```
DEPOSIT|account=<uuid lowercase>|amount=<normalized>
TRANSFER|source=<uuid>|destination=<uuid>|amount=<normalized>
REVERSAL|transaction=<uuid>
```

`normalized` is `amount.stripTrailingZeros().toPlainString()`, so `"100"`, `"100.0"` and `100.00` all hash the same. JSON formatting, key order and unknown fields do not affect the hash.

### 7.4 Flow

```
Controller → IdempotentExecutor (NOT transactional) → PostingService (@Transactional)

1. Validate the header and body syntax.                                400
2. Compute request_hash.
3. Fast path: SELECT the transaction by idempotency_key (own short read transaction).
     found, same hash      → replay: 201 + the original body + the original Location
                             + header Idempotent-Replayed: true (see "Replay response" below)
     found, different hash → 409 idempotency-key-reused
4. Call PostingService.<op>(cmd, key, hash).
5.   Inside: after the account locks (§6.1 step 3), SELECT by idempotency_key again.
       found → throw IdempotencyReplay(existingId). This rolls back; nothing has been written yet.
6.   Inside: INSERT the transactions row (§6.1 step 5).
7. On success → 201 Created, Location: /transactions/{id}
8. catch IdempotencyReplay                        → load it, then replay or 409 by hash (as in step 3)
   catch unique violation on
     transactions_idempotency_key_uq              → in a NEW read transaction, load by key, then replay or 409 by hash
     transactions_reverses_uq                     → 409 transaction-already-reversed
```

Implementation notes:

- **Which constraint failed.** Read it from the `PSQLException`'s `ServerErrorMessage.getConstraint()`. Don't parse message text.
- **Where the catch lives.** The catch and the reload are in `IdempotentExecutor`, a separate bean outside the `@Transactional` proxy. A PostgreSQL transaction that has raised an error is aborted and can't run more queries.
- **Replay response.** A replay returns the **original status (201), the original `Location` and the original body**. The only addition is the `Idempotent-Replayed: true` header. A client that only looks at the status code can't tell a replay from the first response, and doesn't need to.
- **How the body is rebuilt.** The response body is not stored. It is rebuilt from the transaction and its entries, which never change. The one field that can change later is `reversedByTransactionId`, and it is always `null` when a transaction is first created. The replay renders the transaction **as it was created**, with `reversedByTransactionId: null`, so the body matches the original. `GET /transactions/{id}` always shows the current state.

### 7.5 Race analysis

| Scenario | What happens |
|---|---|
| Sequential retry after success | Step 3 finds the key → replay (201 + `Idempotent-Replayed`). |
| Two identical requests at the same time, enough funds | Both lock the same accounts, so B waits. A commits. B's re-check at step 5 sees A's row → replay. |
| Two identical requests at the same time, and A's transfer uses up the funds | Same as above. B's re-check runs **before** its funds check, so B returns a replay instead of a wrong 422. This is why step 5 exists. |
| Same key, different body, overlapping accounts | B waits on the locks. Step 5 finds the key with a different hash → 409. |
| Same key, different body, disjoint accounts | No lock overlap. B's INSERT waits on A's uncommitted unique-index entry. If A commits, B gets a unique violation → reload → 409. If A rolls back, B goes ahead and keeps the key. |
| Same key, different body, B fails validation (for example a 422) before inserting | B returns its own error, not 409. Acceptable: nothing was written. |
| Original request was rejected (4xx) | The key was never stored. A retry is evaluated from scratch and may succeed. |
| Two different keys reversing the same transaction | Both lock the same accounts. The second one's "already reversed" check (after the lock) → 409. `transactions_reverses_uq` is the backstop. |

## 8. HTTP API

> **Every request that moves money needs an `Idempotency-Key` header.**
>
> This applies to `POST /accounts/{id}/deposits`, `POST /transactions` and `POST /transactions/{id}/reversals`.
>
> - Send a new unique value (for example a UUID) for each new request.
> - Send the **same** value when you retry that request.
>
> Without the header the request is rejected with **400** `missing-idempotency-key`, and the response explains why (§7.1). This is how the ledger guarantees that a repeated request never causes a second transfer.
>
> A retry with the same key and body gets the original **201** response again, with `Idempotent-Replayed: true` added. Reusing a key with a different body gets **409**.

### 8.1 Conventions

- Content type is `application/json`. Errors use `application/problem+json` (§9).
- IDs are UUID strings. A path ID that is not a valid UUID → 400.
- Amounts are strings in responses, and strings or numbers in requests (§3.4).
- Created resources return **201** with a `Location` header. An idempotent replay returns the same 201, `Location` and body, plus `Idempotent-Replayed: true` (§7.4).
- Pagination uses `?page=0&size=20`. `page` starts at 0 and must be ≥ 0. `size` must be between 1 and 100 and defaults to 20. Anything else → 400.

|---|---|

## 9. Errors

Every error is a `ProblemDetail` with:

- `type` = `/problems/<code>`;
- `title`, `status`, `detail` and `instance`;
- extra properties where they help. Validation errors carry `errors: [{field, message}]`.

Stack traces and SQL are never returned.

| Code | Status | Raised when |
|---|---|---|
| `validation-error` | 400 | Bean validation fails, the JSON is malformed, a field has the wrong type, or paging parameters are bad |
| `missing-idempotency-key` / `invalid-idempotency-key` | 400 | §7.1 |
| `invalid-amount` | 400 | Amount ≤ 0, above the maximum, or with too many decimals for its currency |
| `same-account` | 400 | Source = destination |
| `invalid-period` | 400 | Period is not `YYYY-MM` |
| `account-not-found` | 404 | |
| `transaction-not-found` | 404 | |
| `reconciliation-not-found` | 404 | |
| `idempotency-key-reused` | 409 | Same key with a different request hash |
| `transaction-already-reversed` | 409 | |
| `reconciliation-in-progress` | 409 | |
| `insufficient-funds` | 422 | |
| `exchange-rate-not-found` | 422 | |
| `amount-too-small` | 422 | The converted amount rounds to 0 |
| `system-account-not-allowed` | 422 | |
| `reversal-not-allowed` | 422 | |
| `period-not-closed` | 422 | The period ended less than 5 minutes ago, or hasn't ended (§12.1) |

3. existence → 404;
4. currency-dependent amount checks → 400;
5. business rules → 422 or 409.

## 10. Exchange rates

### 10.1 Provider

```java
public interface ExchangeRateProvider {
    /** Rate such that 1 {@code base} = rate {@code quote}, effective at {@code at}. */
    Optional<BigDecimal> rateFor(Currency base, Currency quote, Instant at);
}
```

The default implementation is `DatabaseExchangeRateProvider`. It returns the row with the greatest `effective_from` that is ≤ `at`, with ties broken by the greatest `id`.

### 10.2 Rules

- **Directed pairs only [added].** S→D does not fall back to `1 / rate(D→S)`. Inverting would mean choosing a precision and a rounding mode for the inverse, and real buy and sell rates differ anyway. All 12 directed pairs are seeded.
- **The rate is read inside the posting transaction, after the account locks,** and stored on the transaction row as `fx_rate`. A `PUT` running at the same moment affects only transactions that read the rate after it commits.
- **`fx_rate` is the record of truth for which rate a transfer used; the rate history is not.** A `PUT` stamps `effective_from` with its own `now`, before it commits. A transfer that reads the rate between those two moments doesn't see the new rate, even when its `created_at` is later than that `effective_from`. For such a transfer, looking the history up at its `created_at` gives the newer rate, not the one it used. Nothing recomputes a conversion from the history: reversals copy the original entries (§5.4), and responses and history show `fx_rate`.
- **Rate precision** is `NUMERIC(20,10)`. The product `amount × rate` is computed at full precision and then rounded once.
- **Reversals never look up a rate** (§5.4).

### 10.3 Seed data (illustrative)

All rows have `effective_from = '1970-01-01T00:00:00Z'`, so they apply under any test clock.

| base → quote | rate | base → quote | rate |
|---|---|---|---|
| SGD → USD | 0.7412 | USD → SGD | 1.3490 |
| SGD → EUR | 0.6815 | EUR → SGD | 1.4674 |
| SGD → JPY | 111.11 | JPY → SGD | 0.0090 |

## 11. Integrity check (`GET /ledger/integrity`)

The check runs in one `@Transactional(readOnly = true, isolation = REPEATABLE_READ)` method, so every query reads the **same snapshot** **[added]**. Under READ COMMITTED, a transfer that commits between the "balances" query and the "entries" query would show up as a false discrepancy.

| # | Check | Discrepancy reported |
|---|---|---|
| C1 | For each currency, `Σ accounts.balance = 0` | `CURRENCY_NOT_ZERO_SUM` {currency, actual} |
| C2 | For each currency, `Σ entries.amount = 0` | `CURRENCY_ENTRIES_NOT_ZERO_SUM` {currency, actual} |
| C3 | For each account, `balance = Σ entries.amount` (accounts with no entries count as 0) | `CACHED_BALANCE_MISMATCH` {accountId, currency, expected = Σ entries, actual = balance, difference} |
| C4 | For each transaction and currency, `Σ entries.amount = 0` | `TRANSACTION_UNBALANCED` {transactionId, currency, actual} |
| C5 | For each customer account, `balance ≥ 0` | `NEGATIVE_CUSTOMER_BALANCE` {accountId, actual} |
| C6 **[added]** | Each transaction has the expected number of entries: DEPOSIT 2, TRANSFER 2 (no `fx_rate`) or 4 (with one), REVERSAL = the original's count | `UNEXPECTED_ENTRY_COUNT` {transactionId, expected, actual} |
| C7 **[added]** | Each reversal's entries are exactly the original's entries negated, matched by account | `REVERSAL_MISMATCH` {transactionId, accountId, expected, actual} |

The `currencies` block in the response answers the assignment's "total money in the ledger matches the expected sum". Under double entry the expected net is 0. Also, `customerTotal = −(externalTotal + fxPoolTotal)`, so the money held by customers equals the net money brought in from outside plus the house's FX position.

## 12. Month-end reconciliation

### 12.1 Period

- A period is a UTC calendar month `[periodStart, periodEnd)`. For example, `2026-09` is `[2026-09-01T00:00Z, 2026-10-01T00:00Z)`. The end is exclusive.
- A period is accepted only from `periodEnd + 5 minutes` (`closesAt`), by the `Clock`. Before that → 422 `period-not-closed`, which carries `period` and `closesAt`. The current month and later months are always rejected.
- The 5 minutes **[added]** apply to manual runs (`POST /reconciliations`) and the scheduled job alike. Postings take their `created_at` after their locks and commit a moment later, so for a short time after midnight the previous month can still receive entries. A run in that window could miss one, and its snapshot is stored for good: every re-run would then report a false `SNAPSHOT_MISMATCH`, and the next month a false `ROLLFORWARD_MISMATCH`.

### 12.2 Algorithm

The run uses one `REPEATABLE_READ` transaction, so all reads see one snapshot. It covers every account with `created_at < periodEnd`, system accounts included.

```
prev           = snapshot(account, period − 1 month)          -- may be absent
opening        = prev?.closing_balance
                 ?: Σ entries with created_at < periodStart   -- marked openingSource = COMPUTED
activity       = Σ entries with periodStart ≤ created_at < periodEnd
closing        = Σ entries with created_at < periodEnd
closingCount   = COUNT of the same entries

R1  opening + activity = closing          else ROLLFORWARD_MISMATCH   {expected: opening+activity, actual: closing}
R2  if snapshot(account, period) exists:
        closing_balance = closing and entry_count = closingCount
                                          else SNAPSHOT_MISMATCH      {expected: stored, actual: recomputed}
        (the stored snapshot is never overwritten)
    else INSERT snapshot(closing, closingCount)
R3  accounts.balance = Σ all entries      else CACHED_BALANCE_MISMATCH
R4  customer: closing ≥ 0                 else NEGATIVE_CLOSING_BALANCE   [added]
```

The run then saves one `reconciliations` row, one `reconciliation_accounts` line per account checked, and its `reconciliation_discrepancies`, and returns the report.

Each account line shows:

| Field | Value |
|---|---|
| `openingBalance` | `opening` above |
| `openingSource` | `SNAPSHOT` (from `prev`) or `COMPUTED` (no previous snapshot) |
| `movement` | `activity` above |
| `closingBalance` | `closing` above. Equals opening + movement unless R1 failed. |
| `snapshot` | `CREATED` by this run (R2 else-branch), or the existing snapshot `MATCHED` or `MISMATCHED` the recomputed closing |
| `status` | `MATCHED` if the account has no discrepancy in this run, otherwise `DISCREPANCIES_FOUND` |

The report also counts `accountsMatched` and `accountsWithDiscrepancies`. Lines are stored with the report, so `GET /reconciliations/{id}` returns them exactly as the run produced them.

What each check catches. Entries are append-only, so most of these can only fail if something went wrong outside the application:

| Check | Fails when |
|---|---|
| R1 | An entry dated before the period changed after the previous snapshot was taken (`prev.closing ≠ Σ entries < periodStart`) |
| R2 | An entry inside or before this period was added, changed or removed after this period was reconciled. `entry_count` **[added]** catches changes that cancel out in the sum. |
| R3 | The cached balance and the entries have drifted apart |

### 12.3 Concurrency

- Two runs for the same period can collide on `balance_snapshots_account_period_uq`. The loser gets 409 `reconciliation-in-progress`, and its transaction rolls back completely. Running again is safe: it verifies the snapshots the winner wrote.
- Postings that happen during a run don't affect it. They are dated after `periodEnd`, and the run reads one snapshot.
- Postings don't block the run, and the run doesn't block postings. The run's inserts check foreign keys against `accounts` with `FOR KEY SHARE`, which doesn't conflict with the postings' `FOR NO KEY UPDATE` (§6.2). That holds even for accounts whose balance changed after the run's snapshot.

### 12.4 Scheduled job

```java
@Scheduled(cron = "${ledger.reconciliation.cron:0 6 0 1 * *}", zone = "UTC")
```

- Runs at **00:06 UTC** on the 1st of each month and reconciles the previous month, computed with the `Clock`.
- The previous month closes at 00:05 (§12.1). The 5-minute delay **[added]** covers write transactions that took their `created_at` just before midnight but commit just after. Without it, the job could snapshot the month before those entries are visible. A later re-run would then report a false `SNAPSHOT_MISMATCH`. Manual runs get the same delay.
- The job runs a minute later still, at 00:06 **[added]**, so it can never fire before the period closes. A scheduler's trigger and the application `Clock` can disagree by a few milliseconds. At exactly 00:05, a run that fired slightly early would get 422 `period-not-closed`, and that month's scheduled reconciliation would be lost.
- The run is recorded with `trigger = SCHEDULED`.
- If it gets 409, it logs and returns, because another run has the period.
- Failures are logged at ERROR. There is no automatic retry.
- It is enabled by `ledger.reconciliation.scheduling-enabled`, which is `false` in tests.

## 13. Invariants

These must hold after every committed transaction. Each one says where it is enforced.

| # | Invariant | Enforced by |
|---|---|---|
| I1 | The entries of each transaction sum to 0 per currency | Posting rules (§5), pre-commit assertion (§5.6), integrity C4 |
| I2 | For each currency, the sum of all balances is 0 | Follows from I1 and I3; integrity C1/C2 |
| I3 | `accounts.balance = Σ entries.amount` for every account | Balance updated in the same transaction as the entry insert; integrity C3; reconciliation R3 |
| I4 | Customer balances are ≥ 0 | Funds check after locking; pre-commit assertion; DB CHECK `accounts_customer_non_negative`; integrity C5 |
| I5 | Entries and transactions are never updated, deleted or truncated | No such code paths; DB triggers (§4) |
| I6 | An entry's currency is its account's currency | Composite FK `entries_account_currency_fk` |
| I7 | An idempotency key maps to at most one transaction | `transactions_idempotency_key_uq` |
| I8 | A transaction is reversed at most once, and reversals are never reversed | `transactions_reverses_uq`; check after locking; 422 rule |
| I9 | A reversal's entries are exactly the original's, negated | Posting rule (§5.4); integrity C7 |
| I10 | Amounts have no more decimal places than their currency allows; entries are non-zero | Input validation; one HALF_EVEN rounding point; DB CHECK `amount <> 0` |
| I11 | Only posting rules touch system accounts | API validation (§3.3) |
| I12 | A snapshot or reconciliation report, once written, is never changed | DB triggers (§4); reconciliation compares and never overwrites |
| I13 | A rejected request leaves no trace: no rows and no stored key | Single `@Transactional` method; key stored only on the transaction row |

### 14.2 Tests

Integration tests run against Testcontainers PostgreSQL, using one container per JVM (the singleton pattern) and a mutable `Clock`. Most share one database and assert only on rows they created. Tests that tamper with data, or assert a whole-ledger result (the integrity check, reconciliation, and the concurrency tests, which end with `GET /ledger/integrity` = OK), extend `FreshDatabaseTestBase` instead: before each test it creates a new database in the same container, points the application's DataSource at it, runs the Flyway migrations and drops the previous one.

| Area | Tests |
|---|---|
| Posting | Deposit, same-currency transfer and FX transfer produce the entries in §5; the FX example gives 74.16; a HALF_EVEN tie case; every 400/404/409/422 path writes nothing: the `transactions` and `entries` row counts and every account's balance, system accounts included, are the same before and after. Key reused across operations → 409. The "uses up the funds" race from §7.5 → a replay, not 422. A rejected request's key can be reused. |

| Integrity | Clean ledger → OK. Each check is triggered by allowed tampering only (§4 notes), as in the table below. |
| Database guards | `UPDATE`, `DELETE` and `TRUNCATE … CASCADE` are each rejected by the trigger on every append-only table, and every row survives. How each integrity check is triggered in tests:

| Check | Tampering used |
|---|---|
| C1 and C3 | `UPDATE accounts SET balance = balance + 10` on one account |
| C2 and C4 | Insert a transaction whose entries don't sum to zero |
| C6 | Insert a DEPOSIT with three entries that still sum to zero |
| C7 | Insert a REVERSAL whose amounts differ from the original's |
| C5 | Can't be reached through tampering while the `accounts_customer_non_negative` CHECK exists. See the note below the table. |

**The C5 test** temporarily drops a schema constraint, so it follows these rules:

- **Own class.** It lives in its own test class, `NegativeCustomerBalanceIntegrityIT`.
- **`@Isolated`.** The class is annotated with `@Isolated` (`org.junit.jupiter.api.parallel`), so JUnit never runs it alongside another test while the constraint is missing.
- **Steps:**
  1. `ALTER TABLE accounts DROP CONSTRAINT accounts_customer_non_negative`.
  2. Set a customer balance to a negative value.
  3. Call `GET /ledger/integrity` and assert `NEGATIVE_CUSTOMER_BALANCE` (and the C1/C3 discrepancies the change also causes).
- **Cleanup in `finally`, in this order:**
  1. Put the original balance back.
  2. Re-add the constraint with the same name and definition.

  The order matters. `ADD CONSTRAINT` checks existing rows, so it fails while the negative balance is still there.
- **Class comment.** C5 is defence in depth behind the database CHECK. With the constraint in place, a negative customer balance can't be committed. So the only way to test the integrity query is to remove the constraint, and the test exists to prove the query works if the constraint is ever lost (a bad migration, or a manual change to the schema).

**Reconciliation tamper test (backdated transaction).** This test shows that reconciliation catches history being rewritten, without breaking the append-only rule.

1. Set the clock to 2026-09-10. Deposit 100.00 SGD into Alice.
2. Move the clock to 2026-10-02. Reconcile `2026-09`. The status is `BALANCED`, and snapshots are written for Alice and `EXTERNAL_SGD`.
3. Tamper, with `JdbcTemplate` and inserts only:
   - insert a `DEPOSIT` transaction row with `created_at = 2026-09-15T12:00:00Z` (dummy `idempotency_key` and `request_hash`);
   - insert its two balanced entries: Alice +10.00 and `EXTERNAL_SGD` −10.00, same `created_at`;
   - `UPDATE accounts.balance` on both accounts by the same amounts, so the cached balances agree with the entries.
4. Reconcile `2026-09` again. Expect `DISCREPANCIES_FOUND`, with a `SNAPSHOT_MISMATCH` for Alice (stored 100.00 over 1 entry, recomputed 110.00 over 2) and one for `EXTERNAL_SGD`. Expect **no** `CACHED_BALANCE_MISMATCH`, which shows the snapshot check caught this on its own.
5. Check that the stored 2026-09 snapshots are unchanged.
6. Run `GET /ledger/integrity`. It reports OK. The backdated transaction is balanced and consistent, which is why month-end snapshots are needed to detect it.
7. Move the clock to 2026-11-02 and reconcile `2026-10`. Expect a `ROLLFORWARD_MISMATCH` for both accounts. The opening balance comes from the stale September snapshot, but the closing balance includes the backdated entries.

**Known test gaps (accepted).** These paths are covered by code review and the integrity check, but have no dedicated test:

- **Reconciliation `entry_count` on its own (R2).** The backdated tamper test changes both the sum and the count, so a check that ignored `entry_count` would still pass. A test would need tampering that leaves the sum unchanged, such as a balanced pair of entries on one account.
- **Integrity C6 for FX transfers and reversals.** Only the DEPOSIT case is triggered. The "TRANSFER with `fx_rate` = 4 entries" and "REVERSAL = the original's count" branches are not.
- **Integrity C7 when an account appears on one side only.** Only amounts that differ on the same accounts are tested.
- **A reversal racing the destination's spending.** The funds check under the lock is tested sequentially only, not with a concurrent transfer out of the destination.
- **Same key, different body, overlapping accounts, concurrently, end to end.** The re-check after locking returns 409 here. Only the mocked `IdempotentExecutorTest` covers it.

## 15. Assumptions

1. The ledger is an internal service. There is no authentication or authorization, and any caller may create accounts, move money, set rates and run reconciliations.
2. A single application instance runs. All correctness guarantees come from PostgreSQL (row locks, unique constraints, isolation), so several instances would still be correct for postings. The scheduled job, however, would run on each of them; §12.3 makes that safe, though noisy.
3. Supported currencies are fixed at SGD, USD, EUR and JPY. Adding one needs a migration (CHECK constraints, system accounts, rates).
4. An account's currency is set when it is created and never changes. Each account holds one currency.
5. Money enters the ledger only through deposits from `EXTERNAL_<CCY>`. Withdrawals are out of scope; the posting rule would be the mirror of a deposit.
6. A customer account starts at zero. There is no "opening balance" field; use a deposit.
7. "Transfer" in the assignment and `POST /transactions` are the same operation.
8. A transfer amount is always given in the source currency. The destination receives the converted, rounded amount.
9. The rate used is the one the transfer reads when it is posted, and it is stored on the transaction (§10.2). It is quoted as 1 base = rate quote. There is no spread or fee, and the FX pools absorb rounding.
10. Rates can only take effect "now". Future-dated or backdated rates are not supported through the API.
11. Reversals undo the whole transaction. There are no partial reversals or edits. A "correction" is a reversal followed by a new transaction.
12. A reversal can fail (422) if the money has since been spent. Customer balances never go negative, including through a reversal.
13. A reversal is dated when it is posted, never backdated into the original transaction's period.
14. Idempotency keys are global, never expire, and are stored only for successful postings.
15. A replay returns the original status (201), `Location` and body, rendered as the transaction was when it was created (`reversedByTransactionId: null`). The current state is available from `GET /transactions/{id}`.
16. Account history lists entries oldest first and supports offset pagination.
17. "Timestamp" for ordering and periods means the transaction's `created_at` from the application `Clock`, not the database commit time. Under concurrency, history order may differ slightly from commit order.
18. Month-end means the UTC calendar month, whatever the customer's local time zone.
19. If the app is down at 00:06 UTC on the 1st, that month's scheduled reconciliation is missed. It can be run manually. There is no catch-up.
20. The first reconciliation of an account (no previous snapshot) uses an opening balance computed from entries. That is reported as `openingSource = COMPUTED` on the account's line in the report (§12.2), not as a discrepancy.
21. The integrity check and reconciliation report discrepancies but never repair them.
22. Both run synchronously and scan everything, which is acceptable at this project's data sizes.
23. Request bodies may contain unknown JSON fields. They are ignored and are not part of the request hash.
24. The largest amount per request is 10¹² in currency units.
25. The exchange rates seeded in `V3` are illustrative, not market data.

## 16. Review notes

### 16.1 Where this spec departs from, or reads into, the assignment

1. **`Idempotency-Key` is required on every money-moving POST.** *Decided: required.* The assignment's contract for `POST /transactions` is just "source account, destination account, amount", so a caller who follows it exactly will get a 400. The header stays required anyway: without it the service can't guarantee that a repeated request doesn't cause another transfer. To offset this:
   - the 400 is a ProblemDetail that names the header and says why it is needed (§7.1);
   - the API section opens with a callout (§8);
   - every README `curl` example includes the header (§14.3).
2. **Replays return the original 201, `Location` and body, plus `Idempotent-Replayed: true`.** *Decided.* This replaces the 200 in the original brief. (§7.4)
3. **"Total money in the ledger matches the expected sum."** Under double entry, the expected sum is zero per currency, which is true by construction once I1 holds. To make the check meaningful to a reader, the report also shows customer totals against external and FX-pool totals (§11).
4. **Deposits and system accounts are not in the assignment.** They are needed: without them there is no way to put money into the ledger while keeping zero-sum. This is the kind of justified addition the assignment invites.
5. **The assignment says only that transactions "can be reversed".** This spec allows a reversal to fail (422) when the money has moved on, and limits it to one per transaction. These are restrictions the assignment doesn't state. *Decided: keep them.* They are recorded as Assumptions 11–13.

There are no outright contradictions with the assignment.

### 16.2 Gaps in the brief, and how this spec fills them

All accepted at review on 2026-10-14, along with `JdbcClient` and oldest-first history.

1. **Transfers to or from system accounts.** Nothing in the brief stopped `POST /transactions` from using `EXTERNAL_SGD` (allowed to go negative) as a source, which would create money. They are now forbidden (422), and `POST /accounts` creates only customer accounts. (§3.3)
2. **UUID lock order.** "Ascending id order" differs between Java (`UUID.compareTo`, signed) and PostgreSQL (unsigned bytes). Locks are therefore taken in a single `ORDER BY id FOR NO KEY UPDATE` query. (§6.2)
3. **The idempotency race combined with the funds check.** With only "unique constraint + catch", a concurrent duplicate whose twin used up the funds would get **422 instead of a replay**: it waits on the account locks and fails the funds check before it ever reaches the INSERT. The fix is to re-check the key after the locks are taken. (§7.4 step 5, §7.5)
4. **Two unique constraints on `transactions`.** A violation of `reverses_transaction_id` must not be treated as an idempotent replay. The handler branches on the constraint name. (§7.4)
5. **Request-hash definition.** The hash covers the operation type, the path IDs and the normalized amount, so `100` and `100.00` count as the same body. (§7.3)
6. **Status codes the brief didn't give:**
   - already reversed → 409;
   - reversing a reversal → 422;
   - system account in a transfer → 422;
   - current or future reconciliation period, or one that ended less than 5 minutes ago → 422;
   - malformed period → 400;
   - concurrent reconciliation → 409.
7. **The converted amount can round to zero** (for example 1 JPY → EUR at a very low rate). This is rejected with 422 rather than posting a zero entry. (§5.3)
8. **Rate direction and inverses.** The brief has (base, quote, rate) but didn't say how to look up S→D. The spec uses directed pairs only, with no inversion, and seeds all 12. (§10.2)
9. **Read consistency for the integrity check and reconciliation.** Both must use REPEATABLE READ (one snapshot), or concurrent postings produce false discrepancies. The write path, by contrast, must stay on READ COMMITTED. (§6.1, §11, §12)
10. **Entry currency vs. account currency.** Nothing enforced that they match. A composite FK now does. (§4)
11. **Database-level enforcement.**
    - A CHECK keeps customer balances non-negative.
    - Triggers make entries, transactions, snapshots, rates and reconciliation reports append-only, including against `TRUNCATE`.
    - CHECKs tie `type` to `reverses_transaction_id` and `fx_rate`.
12. **Reconciliation details:**
    - the first period has no previous snapshot;
    - existing snapshots are never overwritten;
    - `entry_count` is stored alongside the closing balance;
    - concurrent runs are handled;
    - a period closes 5 minutes after it ends, for manual runs and the job, to allow for late commits; the job runs at 00:06, a minute after that. (§12)
13. **Timestamp precision.** Values are truncated to microseconds so that they still compare equal after a round trip through PostgreSQL. (§3.5)
14. **Account history.** The order is ascending, with entry `id` breaking ties. Each item carries source and destination so it makes sense on its own. (§8.7)
15. **Amount format and limits.** Amounts are JSON strings in responses. Trailing zeros are allowed. The maximum is 10¹². (§3.4)
16. **Data access.** The spec chooses `JdbcClient` over JPA so the locking SQL and the moment a constraint violation is raised are explicit. (§2.1)

### 16.3 Known limitations and possible extensions (not planned)

- **`POST /accounts` is not idempotent.** A retried create can make a duplicate account. An optional `Idempotency-Key` on that endpoint would fix it.
- **System accounts are throughput hot spots** (§6.3).
- **The sum-to-zero rule is enforced only in the application.** A `DEFERRABLE INITIALLY DEFERRED` constraint trigger that checks each transaction's entries at commit would enforce it in the database too.
- **History has no running balance.** A `balance_after` column on `entries`, written under the lock, would give statement-style running balances and one more integrity check.
- **Reversals have no `reason` field.** One could be added to the transaction row (and to the request hash).
- **There is no `GET /accounts` list endpoint.** The fixed system-account UUIDs are documented in §3.3 instead.
- **There is no catch-up for missed scheduled reconciliations** (Assumption 19).
- **The application connects as the role that owns the schema.** The same datasource runs Flyway, so the application's role can `ALTER`, `DROP` or `DISABLE` the append-only triggers and constraints. They guard against mistakes, not against that role. In production, migrations would run as a separate owner role. The application's role would get only `SELECT` and `INSERT` on the ledger tables and `UPDATE (balance)` on `accounts`, so it could neither change the schema nor `TRUNCATE`.
